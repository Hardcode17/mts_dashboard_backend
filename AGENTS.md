# Правила ведения проекта

Проект использует Java 21, Spring Boot и Gradle Kotlin DSL. Базовый пакет — `ru.hardcode.dashboard`. Структура следует `bank-service`; банковские сущности, настройки и инфраструктура не являются частью проекта.

## Структура

- `configuration/` — настройки Spring и безопасность; `configuration/filter/` — servlet-фильтры, `configuration/rest/` — настройки исходящих HTTP-клиентов и их перехватчиков.
- `controller/` — REST-эндпоинты: принимать и валидировать запросы, вызывать сервисы и возвращать DTO. Бизнес-логика не должна жить в контроллерах. Новые бизнес-эндпоинты размещайте под `/api`; существующие URL не меняйте без необходимости.
- `dto/` — контракт HTTP API: отдельные `record` для запросов и ответов (`CreateXRequest`, `XResponse`). Не возвращайте JPA-сущности напрямую.
- `service/` — бизнес-правила и границы транзакций. Для операций только на чтение используйте `@Transactional(readOnly = true)`, когда нужна транзакция.
- `entity/` — JPA-сущности и связанные перечисления; `repository/` — Spring Data репозитории. Когда поиск с выбросом прикладной ошибки повторяется, выносите его в `*RepositoryProxy`.
- `exception/` — прикладные исключения и общая обработка ошибок REST API.
- `src/main/resources/db/migration/` — миграции Flyway (`V1__DESCRIPTION.sql`, `V2__DESCRIPTION.sql` и далее). Уже применённые миграции не редактируйте.
- `src/test/java/ru/hardcode/dashboard/` — тесты; `client/` — переиспользуемые клиенты для интеграционных HTTP-тестов. Не добавляйте фиктивные классы только для заполнения пакетов.

Используйте конструкторное внедрение зависимостей и `final` для полей зависимостей. Сохраняйте форматирование существующего кода.

## Ошибки API

- Описывайте ожидаемые прикладные ошибки в `AppErrors`: стабильный код, HTTP-статус и публичный шаблон сообщения. Не переиспользуйте код для ошибки с другим смыслом.
- Выбрасывайте `AppException` там, где обнаруживается ошибка. Передавайте значения для `${name}` через `Map.of(...)`; причину исключения сохраняйте, когда она есть.
- `GlobalExceptionHandler` (`@RestControllerAdvice`) преобразует `AppException` в `AppErrorResponse` (`{"code":"…","message":"…"}`). Не дублируйте обработку в контроллерах. Ошибки из фильтров безопасности и servlet-фильтров не проходят через advice автоматически.
- Не раскрывайте в сообщениях секреты, персональные данные, SQL, трассировки стека и внутренние детали. Не перехватывайте все исключения ради подмены ошибок Spring MVC.

## Логи

- `LoggerFilter` создаёт `requestId`, помещает его в MDC и возвращает в `X-Request-Id`. Логируйте метод, путь без query string, статус и время обработки. Не логируйте заголовки, параметры и тела ответов.
- `request-logging.max-cached-body-size` ограничивает JSON-тела (по умолчанию `1MB`); превышение возвращает `413` с кодом `REQUEST_BODY_TOO_LARGE`. Multipart и другие типы контента этим фильтром не ограничиваются.
- `request-logging.log-request-body` по умолчанию выключен. Включайте только локально с тестовыми данными и уровнем `DEBUG` для `ru.hardcode.dashboard.configuration.filter.LoggerFilter`: в лог попадут первые 4 КБ JSON.
- Logback пишет в stdout и `./logs/dashboard.log`. Ротация настраивается через `logging.logback.rollingpolicy`, путь — через `logging.file.name`. Каталог `logs/` не коммитится.

## Проверки

- Запускайте тесты через Gradle Wrapper: `.\gradlew.bat test` на Windows, `./gradlew test` на Linux/macOS. Выборочный запуск: `.\gradlew.bat test --tests "*GlobalExceptionHandlerTest"`.
- HTTP-контракты проверяйте через MockMvc: статус и JSON, для прикладных ошибок — оба поля `code` и `message`. Для проверки только MVC не подключайте БД и внешние сервисы.
- Интеграционные тесты с реальными зависимостями называйте `*IT` и переиспользуйте `TestcontainersConfiguration`; для них нужен работающий Docker.
- Секреты задавайте через окружение, не коммитьте их. Не отключайте безопасность глобально ради тестовых эндпоинтов.
