# Очередь значимых событий смены (KAN-25)

Дюраблная очередь значимых событий смены: детекция переходов INC из журнала изменений,
устойчивые `eventId`, данные для оповещения и признак «требует Увидел». Потребители:
экран смены, подтверждение показанных событий (KAN-29), доставка оповещений (KAN-35).

## Чтение очереди

```
GET /api/dashboard/shift/events?sinceEventSeq=0&limit=100
```

- Человек-цепочка координатора (`/api/dashboard/**`, Bearer JWT + локальный допуск), как
  остальные чтения дашборда.
- Возвращает **оставшуюся** очередь: события с `eventSeq > sinceEventSeq` без подтверждения
  «Увидел» (после ack подтверждённые события из очереди исчезают), по возрастанию.
  `nextEventSeq` — курсор следующего опроса; без новых событий он равен поданному
  `sinceEventSeq`. Не-сигнальные события (`ackRequired = false`) не подтверждаются и
  остаются в очереди видными для оповещений (KAN-35); полноэкранный сигнал UI выбирает по
  `ackRequired = true`.
- `limit` 1..500 (по умолчанию 100). Ошибки: `INVALID_EVENT_SEQ` (отсутствует, не число,
  отрицательное или вне int64), `INVALID_EVENT_LIMIT`.
- Каждый опрос сначала доводит очередь до актуальности (курсорная обработка журнала — см.
  ниже), поэтому событие становится видно при первом же опросе после публикации.

```json
{
  "events": [
    {
      "eventId": "evt-0007",
      "eventSeq": 7,
      "incidentId": "INC000021095603",
      "reasons": ["became_critical", "assigned_to_coordinators"],
      "ackRequired": true,
      "changeRevision": 12,
      "sourceId": "itcs-prod",
      "occurredAt": "2026-11-21T09:05:01.000000Z",
      "incident": {
        "id": "INC000021095603", "header": "…", "productName": "…",
        "stateEnum": "Assigned", "priorityId": 4, "submitDate": "…", "deadline": "…",
        "completionDate": null, "solution": null,
        "assignedGroupName": "КЦ ИТ Координаторы Массовых Инцидентов", "assignedEmployee": "…"
      }
    }
  ],
  "nextEventSeq": 7
}
```

## Причины событий

Коды стабильны и совпадают с `reasons[]` строки `shift_event`:

| Код | Переход | Требует «Увидел» |
| --- | --- | --- |
| `new_critical` | впервые наблюдаемый активный INC с `priorityId = 4` (ADDED/RETURNED) | да |
| `became_critical` | активный INC повышен до `priorityId = 4` | да |
| `critical_reopened` | критический INC вернулся в работу из завершённого состояния | да |
| `assigned_to_coordinators` | INC вошёл в ITSM-группу «КЦ ИТ Координаторы Массовых Инцидентов» | нет |
| `critical_resolved` | явный `Resolved` критического INC при активном `before` | нет |

`ackRequired = true` только у трёх сигнальных причин (полноэкранное оповещение по ТЗ).
Вход на координаторов и решение — события очереди для оповещения, не сигналы тревоги.

Все причины одного обновления INC объединяются в **один** `eventId` с общим
`changeRevision` (например, повышение до P4 + назначение координаторам за одну ревизию —
один ID с `["became_critical", "assigned_to_coordinators"]`).

## Контракт `eventId` (для KAN-29)

- Формат: `evt-` + минимум 4 цифры (`^evt-[0-9]{4,}$` — как `eventId` в
  `dashboard-api.openapi.yaml`), номер из последовательности `shift_event_id_seq`.
- Присваивается один раз при создании строки. Повторная обработка той же ревизии
  (повтор пакета, рестарт, потерянный курсор) ничего не меняет: дедуп по
  `UNIQUE (source_id, incident_id, change_revision)`.
- Пропуски номеров допустимы и ничего не значат: конфликтная вставка расходует номер
  последовательности без записи. Уникальность гарантируют ограничения, а не непрерывность.
- Новое открытие того же INC — новая ревизия → новый `eventId` (решение `evt-N`, возврат
  в работу — `evt-M ≠ N`).
- Подтверждение «Увидел» (KAN-29) принимает точный набор показанных `eventId` именно с
  `ackRequired = true`; сама очередь ничего не подтверждает.

## «Увидел» (KAN-29)

```
POST /api/dashboard/shift/events/ack
{"eventIds": ["evt-0001", "evt-0002"]}
```

- Человек-цепочка координатора; автор подтверждения — вошедший координатор
  (`users.id`), время — серверное; оба хранятся в `shift_event.acknowledged_by/at`
  для общего экрана.
- Тело: точный набор 1..1000 уникальных `evt-` идентификаторов. Ответ:

```json
{
  "status": "acknowledged",
  "confirmedEventIds": ["evt-0001", "evt-0002"],
  "events": [ ...оставшаяся очередь в формате ShiftEventResponse... ],
  "nextEventSeq": 3
}
```

Правила:

- **Атомарность и точность.** Каждый id обязан быть существующим сигнальным событием
  (`ackRequired = true`): неизвестный → `400 ACK_EVENT_UNKNOWN`, не-сигнальный →
  `400 ACK_EVENT_NOT_ALARM` — и ничего из набора не подтверждается. Подтверждается ровно
  перечисленное: событие C, пришедшее одновременно с ack(A,B), остаётся
  неподтверждённым, и его повтор ack(A,B) не задевает.
- **Идемпотентность и атрибуция.** Повтор запроса (любым оператором) не меняет автора и
  время первого подтверждения; рестарт сохраняет результат. Новый критический эпизод
  того же INC — другой `eventId` — подтверждается отдельным запросом.
- **Окно обзора** — политика клиента (демо: 30 с): сервер принимает набор независимо от
  давности показа, UI сам решает, какие показанные события собрать в ack.
- **Ack не принимает внутреннюю задачу** и не закрывает её (`coordination_tasks` не
  трогается — серверное правило KAN-32).

## Идемпотентность и базовый снимок

Детекция курсорная: `shift_event_progress.last_revision` + чтение журнала через порт
(ниже). Курсор двигается только вперёд; обработка идемпотентна.

- **Первый полный снимок источника — базовый и событий не создаёт**: ревизия первого
  изменения источника фиксируется в `shift_event_source.baseline_revision`, строки с
  ревизией `<= baseline` пропускаются. Уже активные P4 в первом снимке не «новые
  критические».
- **Пропажа строки** (MISSING) никогда не создаёт сигнала.
- **Изменение только описания** — строка UPDATED без подходящих причин — тоже.
- ADDED и RETURNED несут `before = null`, поэтому для них работают только правила
  «новое наблюдение» (`new_critical`, `assigned_to_coordinators`); правила переходов
  (повышение, повторное открытие, решение) требуют `before` и применяются к UPDATED.

## Контракт с KAN-28 (чтение изменений INC)

Детекция потребляет только внутренний порт
`ru.hardcode.dashboard.service.ItsmIncidentChangeFeed`:

```java
List<IncidentChange> afterRevision(long afterRevision, int limit);

record IncidentChange(long revision, String sourceId, long sourceVersion, String incidentId,
                      ChangeKind kind, Map<String, Object> before, Map<String, Object> after);
enum ChangeKind { ADDED, UPDATED, MISSING, RETURNED }
```

Строки журнала по возрастанию ревизии, `before`/`after` — нормализованные записи INC.
Сейчас порт закрыт адаптером `JdbcItsmIncidentChangeFeed`, читающим существующий журнал
`itsm_incident_change` (его пишут публикация снимков KAN-55 и правки координатора
KAN-22/KAN-57). Когда KAN-28 отдаёт историю по курсору, адаптер заменяется за тем же
портом — детекция, `eventId` и контракт очереди не меняются. Возврат строки после
пропажи (RETURNED) трактуется как новое наблюдение и может снова дать
`new_critical`/`assigned_to_coordinators` с новым `eventId`.

## Схема (V8__shift_event_queue.sql, V10__shift_event_ack.sql)

- `shift_event` — события; `event_id` уникален, `reasons text[]`, `ack_required`,
  `payload jsonb` (данные оповещения INC после изменения), дедуп
  `(source_id, incident_id, change_revision)`; с V10 — `acknowledged_by` (KAN-29, автор
  первого «Увидел», никогда не перезаписывается) и `acknowledged_at` (время первого
  подтверждения), частичный индекс `ix_shift_event_pending` по непоподтверждённым.
- `shift_event_source` — базовая ревизия каждого источника.
- `shift_event_progress` — синглтон-курсор детекции.
- Нумерация: V8 — очередь KAN-25; V9 — история изменений INC (KAN-28); V10 —
  подтверждения KAN-29.
